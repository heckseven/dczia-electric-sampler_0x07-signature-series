# Task 3 baseline - 2026-08-31

Taken by the badge on itself, driven by `Spikes/host/run_baseline.py`, with nobody
touching it. Firmware under test is `heckseven/sampler-rework` at `491294d`.

Three runs. The first two are kept because the difference between them is the finding.

| run | state machine | loop p50 | loop p99 | loop max | collections / 4000 | GC p50 | free after GC |
|---|---|---|---|---|---|---|---|
| 1 | absent | 7.0 ms | 15.7 ms | 33.4 ms | 6 | 15.3 ms | 73,440 |
| 3 | **attached** | **8.5 ms** | **40 ms** | **46.1 ms** | **132** | **25 ms** | 23,088 |

Run 3 is the shipping loop. Run 1 measured `engine.tick()` and would have been reported
as "the loop" if the caveat had not been chased.

## The main loop is 8.5 ms typical and 40 ms at the 99th percentile

**measured**, run 3: `min=6896 p50=8500 p90=11500 p99=40000 max=46112` microseconds
over 4,000 passes, transport playing a four-track pattern, sampler screen up.

This settles a contradiction the repo has carried:

| source | claim | verdict |
|---|---|---|
| `sequencer.py:237` | "a main loop that is otherwise around 200 us" | **wrong by ~40x** |
| `handoff-2026-08-28.md:171` | ~125 passes/s while streaming, i.e. 8 ms | correct |
| `streaming-bug-rootcause.md:706` | 3000 passes in 20.32 s, i.e. 6.8 ms | correct, engine-only |

Two consequences, and they are the reason the rewrite exists:

- **A pad cannot be serviced faster than this loop.** At 8.5 ms typical, the keypad's
  20 ms scan interval is one term alongside a comparable one, not the whole story.
- **The tail exceeds the audio buffer.** p99 is 40 ms and the worst pass is 46 ms,
  against a 32 ms buffer. Roughly one pass in a hundred is longer than the audio the
  DMA has queued. The bucket counts locate it: 120 passes in 30-40 ms and 12 in
  40-60 ms, on top of a bulk that sits at 6.75-10.25 ms.

## The loop's entire tail is the garbage collector

**measured**, and it is an exact match rather than a correlation:

| bucket | passes |
|---|---|
| under 20 ms | 3,868 |
| 20-25 ms | 0 |
| 25-30 ms | 0 |
| **30-40 ms** | **120** |
| **40-60 ms** | **12** |
| over 60 ms | 0 |
| **tail total** | **132** |
| **collections in the same run** | **132** |

Every slow pass is a pass that collected, and every collection made a slow pass. Nothing
else in the loop - not a display frame, not a card read - produces a pass over 20 ms.

The arithmetic agrees: a normal pass is 8.5 ms and a collection is 24-26 ms, so a pass
containing one lands at 32-35 ms, which is the 30-40 ms bucket where 120 of them are.

So the loop is bimodal rather than variable. That matters for the rewrite: there is one
cause to remove, and removing it leaves a loop whose worst case is about 20 ms rather
than 46. It also means the audio buffer is not being overrun by ordinary work - it is
overrun 132 times in 4,000 passes by one thing.

## Attaching the UI triples the collection rate

**measured.** 6 collections per 4,000 passes with the engine alone; **132** with the
state machine attached - about one pass in thirty. `free_floor` fell from 18,448 to
15,360, i.e. onto `main.py`'s `GC_FLOOR` of 16,384.

The display, the LED animation and the menu are what allocate. This is the mechanism
behind every memory problem in `streaming-bug-rootcause.md`, now with a rate attached.

## The body is about evenly split, and the UI is bimodal

**measured**, 1,898 passes with collections excluded (a collection lands inside whichever
half was running and would smear 25 ms across one of them at random):

| | p50 | p90 | p99 | max |
|---|---|---|---|---|
| `engine.tick()` | 2.0 ms | 3.25 ms | 5.0 ms | 8.3 ms |
| `machine.update()` | 1.5 ms | 3.75 ms | **7.75 ms** | **14.7 ms** |

Two things worth saying plainly.

**They do not sum to the 8.5 ms pass.** 2.0 + 1.5 is 3.5, so roughly half the typical
pass is neither - it is `guard.feed()`, the `gc.mem_free()` check, and whatever the loop
costs around them. That is a larger residual than expected and has not been attributed.

**The UI is bimodal where the engine is not.** 1,140 of 1,898 passes fall in a single
250 us bucket - the dirty-flag gating doing its job, rendering nothing - and then a
second cluster sits at 5-6 ms with a tail to 14.7 ms, which is a display frame being
sent. So the screen is nearly free most passes and costs more than the whole engine on
the passes it is not.

For the rewrite: the UI's worst pass is almost double the engine's, and it is the half
that is *supposed* to be interruptible. A design that gives audio its own core does not
care, which is the point - but a design that does not would have to bound this.

## Collection cost is a function of heap occupancy, not a constant

**measured.** Two figures that looked contradictory are both right:

| heap after collect | collection cost |
|---|---|
| 73,440 bytes free (engine only) | 14.4 - 16.3 ms |
| 23,088 bytes free (UI attached) | **23.7 - 26.0 ms** |

The second matches `handoff-2026-08-28.md:169`'s 25-27 ms, which was measured on a
badge in the same state. **A collection costs most of the audio buffer when the badge is
actually being used**, and the rewrite should treat the figure as occupancy-dependent
rather than quoting a single number.

## time.monotonic_ns() resolves to ~30.5 us

**measured.** `min_step_ns` and `median_step_ns` are both 30,518 ns - exactly 1/32768 s.
`backwards=0` over 2,000 samples.

Fine for millisecond-scale work, quietly wrong for anything finer, which is why the case
runs before anything is timed with it. Every figure here is quoted at that granularity;
the percentiles are bucket-resolution (250 us below 20 ms) and reported as upper bounds
rather than interpolated.

## The keypad constants cannot be read from the object

**not measured.** `interval=unreadable debounce_threshold=unreadable`.
`keypad.KeyMatrix` exposes neither.

So the 20 ms scan interval in `streaming-bug-rootcause.md` section 16 remains **inferred
from upstream CircuitPython source**, and the badge runs a DCZia-supplied `.uf2` of
unrecorded provenance. Closing it needs a timing experiment - drive key events and look
for a detection-delay distribution uniform over one scan interval - not a property read.

## Confirmed from the live objects

**measured.** `key_count=12`, `mixer_voices=18`, `mixer_rate=16000`,
`ram_budget=32768`, `ram_used=32768` (the kit exactly fills its budget), `midi_poll_ms=2`.

`MIDI_POLL_MS = 2` is the *serial* MIDI poll; the USB MIDI poll is a separate 20 ms
constant and is the one that will quantise the planned MIDI-stimulus measurement.

## Notes on method

Three things bit during this run and are now handled in the harness, because each would
have cost a session:

- **Deploying to CIRCUITPY triggers auto-reload**, restarting `main.py` after the
  interrupt. The first run produced no records at all and looked like a broken spike
  rather than one that was never started. `Badge.repl()` now interrupts and proves it
  has a prompt.
- **A marker that appears in the command echo matches instantly.** `>>>` let the next
  command run before the import had finished. Markers are now bare tokens followed by a
  newline, which the echo never produces.
- **A REPL left from a previous run holds the old module**, so `import spike_baseline`
  silently re-ran the previous build - which reads as an edit that did not take. The
  runner now resets before importing, which also puts the badge through its real boot.

And one that changed the spike itself: keeping 4,000 samples in a list allocated 16 KB
and died with `MemoryError` the moment the state machine was attached. Timings now
stream into pre-allocated buckets, so measuring the loop does not change what the loop
has to work with.
