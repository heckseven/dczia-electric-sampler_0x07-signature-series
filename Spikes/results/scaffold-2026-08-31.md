# Task 2 scaffold, first C run - 2026-08-31

Variant (a) only: CDC, both cores, SysTick, the watchdog/scratch recovery contract.
Deliberately not a nine-peripheral bring-up - that would prejudge the C-versus-Rust
question and make "free SRAM" mean whatever that particular driver set allocated.

Raw records:

```
SPIKE  name=scaffold version=1 reset=watchdog
RESULT case=identity core1=1 sys_clk_hz=125000000
RESULT case=memory   variant=cdc data=2856 bss=3248 stack=8192 gap=0 flash=28412
RESULT case=systick  us=1000 cycles=125512 wrapped=0 sys_clk_hz=125000000
DONE   spike=scaffold
```

## 249.9 KB usable, against CircuitPython's 30.2 KB

**measured**, from `arm-none-eabi-nm` on the ELF rather than from the runtime probe, so
the numbers are the linker's:

| region | bytes | address |
|---|---|---|
| `.data` | 2,856 | 0x200000C0-0x20000BE8 |
| `.bss` | 3,248 | 0x20000BE8-0x20001898 |
| **free** | **255,848** | 0x20001898-0x20040000 |
| `SCRATCH_X` (core1 stack) | 4,096 | 0x20040000 |
| `SCRATCH_Y` (core0 scratch) | 2,048 | 0x20041000 |
| core0 stack | 2,048 | 0x20041800-0x20042000 |
| **total** | **270,336** (264 KB) | |
| **fixed overhead** | **14,296** | |

Flash image is 28,412 bytes.

Against CircuitPython's `free after warm: 30224`, that is **8.5x more usable SRAM**. At
16 kHz mono 16-bit - 32 KB/s - the comparison in the units that matter:

| | sample memory | audio |
|---|---|---|
| CircuitPython, as shipped | 32 KB budget | 1.02 s |
| bare-metal C, CDC only | 249.9 KB | 8.0 s |

This is the number behind the whole run of memory failures in
`streaming-bug-rootcause.md` - the kit, the sample browser and the settings tree
competing for about 54 KB. It is also, deliberately, an upper bound: TinyUSB MIDI, MSC,
FatFS, an SD block cache, PIO programs and the audio buffers all come out of the 249.9 KB
and none of them are measured yet. Variants (b) and (c) exist to spend it.

## The clock is 125 MHz, not 133

**measured.** `sys_clk_hz=125000000`, twice.

The planning documents assumed 133 MHz throughout. Everything derived from a cycle count
needs the 125 MHz divisor, and SysTick's 24-bit range covers **134 ms**, not the 126 ms
recorded in `rewrite-phase0-plan.md`.

## SysTick works as a cycle counter

**measured.** A 1,000 us `busy_wait_us` read 125,512 cycles against 125,000 expected -
0.4% high, which is the call overhead around the wait. `wrapped=0`.

Cortex-M0+ has no DWT CYCCNT, so this is the only cycle source available, and it counts
down from a 24-bit reload. Anything timed with it has to fit in 134 ms.

## The recovery contract works, and was proven by using it

**measured**, and by accident rather than design: `reset=watchdog` on the record above.

The badge was flashed, then left alone while the host stayed silent. After
`SPIKE_HEARTBEAT_MS` the firmware reset itself, the host reconnected, and the boot
banner was captured. That is exactly the failure the plan's critique said the watchdog
alone would not catch - USB dead or host gone, CPU alive and happily feeding the dog -
and the heartbeat turned it into a recoverable reset.

Not yet proven: the fault matrix (`__disable_irq` spin, a `udf` hard fault, a deliberate
TinyUSB teardown). Only the heartbeat leg has been exercised.

## Notes

- `gap=0` in the runtime record is not a finding. The SDK's default layout puts
  `__HeapLimit` at `__StackLimit`, so the gap between them is zero by construction; the
  useful figure is bss-end to heap-limit, which is what the table above reports.
- Core 1 was launched and idles. It costs `SCRATCH_X` either way, and the rewrite's
  premise is that audio gets its own core, so a scaffold that never started one would
  under-report by a stack.
- Flashing this spike does **not** erase the CIRCUITPY filesystem: it writes
  0x10000000-0x10006F00, 28 KB at the bottom of a 2 MB flash. Restoring
  `Firmware/DCZiaSampler.uf2` **does** - that image spans the whole 2 MB - so returning
  to CircuitPython costs a redeploy of the firmware and the four flash samples, both of
  which are in git. Songs, kits and `settings.prefs` live on the SD card and survive
  either way.

## The archived restore image is the wrong CircuitPython

**measured**, by restoring it and reading `boot_out.txt`:

```
Adafruit CircuitPython 8.2.2 on 2023-08-01; Raspberry Pi Pico W with rp2040
```

The badge had been running 10.2.1. `Firmware/DCZiaSampler.uf2` is a 2023 image carrying
DCZia's stock firmware as loose `.py` files, and flashing it:

- downgraded CircuitPython two major versions, so the rework could not run - it needs
  `i2cdisplaybus`, introduced in 9;
- put `MenuState.py`, `SequencerState.py` and the rest of the pre-rework design back on
  the volume, where they shadow a later deploy because `Tools/build.py` only copies and
  never removes; and
- rewrote the whole 2 MB, filesystem included.

`build.py` caught it rather than producing a broken badge - it compares `boot_out.txt`
against the compiler and refused, which is the check earning its keep.

The working return path, all host-driven, is: flash stock CircuitPython 10.2.1 for
`raspberry_pi_pico_w`, clear the volume, then `Tools/build.py`. Restored and verified:
`free after warm: 31328, kit 31934`, no traceback.

This matters beyond the inconvenience. The plan's residual-risk section named the
archived `.uf2` as the rollback, and the golden-vector corpus in a later phase depends on
the current Python staying runnable to generate vectors from. Both were resting on an
image that does not restore the thing they need.
