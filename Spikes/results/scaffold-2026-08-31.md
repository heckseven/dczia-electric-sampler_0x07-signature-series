# Task 2 scaffold, first C run - 2026-08-31

Variant (a) only: CDC, both cores, SysTick, the watchdog/scratch recovery contract.
Deliberately not a nine-peripheral bring-up - that would prejudge the C-versus-Rust
question and make "free SRAM" mean whatever that particular driver set allocated.

Raw records:

```
SPIKE  name=scaffold version=1 reset=watchdog
RESULT case=identity core1=1 sys_clk_hz=125000000
RESULT case=memory   variant=cdc data=2856 bss=3248 stack=8192 gap=0 flash=28412
RESULT case=systick  us=1000 cycles=125512 wrapped=0 sys_clk_hz=125000000
```

## 246.8 KB usable, against CircuitPython's 30.2 KB

**measured**, from the ELF's section headers and boundary symbols rather than from the
runtime probe:

| region | bytes | address |
|---|---|---|
| `.ram_vector_table` | 192 | 0x20000000 |
| `.data` | 3,976 | 0x200000C0-0x20001048 |
| `.bss` | 3,248 | 0x20001048-0x20001CF8 |
| `.heap` (SDK default) | 2,048 | 0x20001CF8-0x200024F8 |
| **free, contiguous** | **252,680** | 0x200024F8-0x20040000 |
| core1 stack, in `SCRATCH_X` | 2,048 | 0x20040000 |
| core0 stack, in `SCRATCH_Y` | 2,048 | 0x20041000 |
| unused scratch | 4,096 | 2 KB in each bank, not contiguous with the above |
| **total** | **270,336** (264 KB) | |

**Correction to the first version of this file**, which reported 255,848 free and
249.9 KB. That came from reading `__bss_end__` as 0x20001898; it is 0x20001CF8, and the
2 KB SDK heap sits above it. It also credited `SCRATCH_X` with a 4,096-byte core1 stack,
where the linker gives each core 2,048 and leaves 2 KB spare in each bank. The corrected
figure is **252,680 bytes**, or 254,728 if a design that never calls `malloc` reclaims
the default heap. Nothing downstream changes - the ratio moves from 8.5x to 8.4x - but
the number was published as measured and was wrong in its derivation.

Against CircuitPython's `free after warm: 30224`, that is **8.4x more usable SRAM**. At
16 kHz mono 16-bit - 32,000 bytes/s - in the units that matter:

| | sample memory | audio |
|---|---|---|
| CircuitPython, as shipped | 32 KB budget | 1.02 s |
| bare-metal C, CDC only | 246.8 KB | 7.9 s |

This is the number behind the whole run of memory failures in
`streaming-bug-rootcause.md` - the kit, the sample browser and the settings tree
competing for about 54 KB.

## What the USB classes cost: 1,080 bytes for all of them

**measured**, link-only, by diffing section sizes and then attributing the difference to
named symbols. These builds are never flashed: the figure wanted is the *fixed* SRAM a
class declares at file scope, which is settled at compile time, and descriptors that
would make them enumerate live in flash rather than SRAM.

| variant | `.data` | `.bss` | total | delta | what grew |
|---|---|---|---|---|---|
| (a) CDC | 3,976 | 3,248 | 7,224 | - | - |
| (b) + MIDI | 3,976 | 3,576 | 7,552 | **+328** | `_midid_itf` 200, `_midid_epbuf` 128 |
| (c) + MIDI + MSC | 4,152 | 4,152 | 8,304 | **+752** | `_mscd_epbuf` 512, `_mscd_itf` 64, plus 176 of initialised SCSI tables |

The buffer sizes are the overhead, so they were chosen explicitly rather than inherited:
64-byte MIDI RX/TX/EP, which is one full-speed bulk packet and what `pico_stdio_usb`
already uses for CDC, and a 512-byte MSC endpoint buffer, one SD block.

**All three classes together cost 1,080 bytes - 0.4% of the free pool.** USB is not a
consideration in the memory budget, which is the useful form of this answer.

**Not measured: FatFS and an SD block cache.** The SDK does not vendor FatFS, so variant
(c) is MSC's own footprint and not the filesystem behind it. That figure follows from
`FF_MAX_SS` and the volume count once a filesystem is actually chosen - one `FATFS`
struct plus a sector-sized window each - and it is a deliberate gap rather than an
oversight. Task 6 measures the card through a raw block driver for the same reason:
FatFS reentrancy is what broke streaming in the Python, and putting it back would measure
the layer that failed rather than the card underneath.

## The clock is 125 MHz, not 133

**measured.** `sys_clk_hz=125000000`, twice.

The planning documents assumed 133 MHz throughout. Everything derived from a cycle count
needs the 125 MHz divisor, and SysTick's 24-bit range covers **134 ms**, not the 126 ms
recorded in `rewrite-phase0-plan.md`.

## SysTick works as a cycle counter

**measured.** A 1,000 us `busy_wait_us` read 125,512 cycles against 125,000 expected -
0.4% high, which is the call overhead around the wait. `wrapped=0`.

Cortex-M0+ has no DWT CYCCNT, so this is the only cycle source available, and it counts
down from a 24-bit reload. Anything timed with it has to fit in 134 ms.

## The recovery contract works, and was proven by using it

**measured**, and by accident rather than design: `reset=watchdog` on the record above.

The badge was flashed, then left alone while the host stayed silent. After
`SPIKE_HEARTBEAT_MS` the firmware reset itself, the host reconnected, and the boot
banner was captured. That is exactly the failure the plan's critique said the watchdog
alone would not catch - USB dead or host gone, CPU alive and happily feeding the dog -
and the heartbeat turned it into a recoverable reset.

Not yet proven: the fault matrix (`__disable_irq` spin, a `udf` hard fault, a deliberate
TinyUSB teardown). Only the heartbeat leg has been exercised.

## Notes

- `gap=0` in the runtime record is not a finding. The SDK's default layout puts
  `__HeapLimit` at `__StackLimit`, so the gap between them is zero by construction; the
  useful figure is bss-end to heap-limit, which is what the table above reports.
- Core 1 was launched and idles. It costs `SCRATCH_X` either way, and the rewrite's
  premise is that audio gets its own core, so a scaffold that never started one would
  under-report by a stack.
- Flashing this spike does **not** erase the CIRCUITPY filesystem: it writes
  0x10000000-0x10006F00, 28 KB at the bottom of a 2 MB flash. Restoring
  `Firmware/DCZiaSampler.uf2` **does** - that image spans the whole 2 MB - so returning
  to CircuitPython costs a redeploy of the firmware and the four flash samples, both of
  which are in git. Songs, kits and `settings.prefs` live on the SD card and survive
  either way.

## The archived restore image is the wrong CircuitPython

**measured**, by restoring it and reading `boot_out.txt`:

```
Adafruit CircuitPython 8.2.2 on 2023-08-01; Raspberry Pi Pico W with rp2040
```

The badge had been running 10.2.1. `Firmware/DCZiaSampler.uf2` is a 2023 image carrying
DCZia's stock firmware as loose `.py` files, and flashing it:

- downgraded CircuitPython two major versions, so the rework could not run - it needs
  `i2cdisplaybus`, introduced in 9;
- put `MenuState.py`, `SequencerState.py` and the rest of the pre-rework design back on
  the volume, where they shadow a later deploy because `Tools/build.py` only copies and
  never removes; and
- rewrote the whole 2 MB, filesystem included.

`build.py` caught it rather than producing a broken badge - it compares `boot_out.txt`
against the compiler and refused, which is the check earning its keep.

The working return path, all host-driven, is: flash stock CircuitPython 10.2.1 for
`raspberry_pi_pico_w`, clear the volume, then `Tools/build.py`. Restored and verified:
`free after warm: 31328, kit 31934`, no traceback.

This matters beyond the inconvenience. The plan's residual-risk section named the
archived `.uf2` as the rollback, and the golden-vector corpus in a later phase depends on
the current Python staying runnable to generate vectors from. Both were resting on an
image that does not restore the thing they need.

## PIO: 12 instructions of 64, and instructions are not the binding resource

**measured**, by counting the assembled programs rather than estimating them. The plan
flagged instruction slots as the constraint - 32 per block, shared by that block's four
state machines - rather than the state machines themselves. On this workload neither
binds:

| program | instructions | state machines | source |
|---|---|---|---|
| `i2s_out` | 8 | 1 | `Spikes/c/i2s.pio`, written for Task 5 |
| `ws2812` (NeoPixel) | 4 | 1 | pico-sdk `pico_status_led/ws2812.pio` |
| **shipped total** | **12 of 32 in one block** | **2 of 4** | |
| `data_watch` | 2 | 1 | measurement only - not shipped |

A single PIO block carries I2S and the ten NeoPixels with **20 instruction slots and two
state machines spare**, and `pio1` is untouched: 32 more slots and four more state
machines for encoders or anything else a later phase wants.

The badge's other inputs do not need PIO at all. The key matrix is a GPIO scan, and the
two rotary encoders can be GPIO interrupts - CircuitPython's `rotaryio` spends a PIO
state machine on each only because that is how the library is built, not because the
hardware requires it.

## The fault matrix: three legs, three recoveries, no hands

**measured.** The matrix drives itself - each boot reads the next leg from watchdog
scratch register 3, reports the previous leg's verdict, then injects. Three deliberate
deaths in about seventy seconds, with the host only listening:

| leg | how it dies | caught by | recovered |
|---|---|---|---|
| `interrupts_off` | `cpsid i` then spin forever | watchdog | **yes** |
| `hard_fault` | `udf #0` into the default handler | watchdog | **yes** |
| `usb_dead` | USB IRQ disabled, loop healthy, dog fed | heartbeat | **yes** |

The first leg matters most for the campaign: **masking interrupts does not save the
firmware from the watchdog**, which runs on its own clock. If it had, nothing that
disables interrupts - the flash-write path in Task 5, for one - would be safe to run
unattended.

### What the reset cause can and cannot prove

Every leg reports `reset=watchdog`, including `usb_dead`. That is not the heartbeat leg
failing to be different: the heartbeat's remedy *is* `watchdog_reboot()`, so it presents
as a watchdog reset. The reset cause cannot distinguish the two mechanisms.

The distinction is proved by construction instead. The `usb_dead` loop calls
`watchdog_update()` every ten milliseconds, so the 8 s watchdog cannot expire - and it
still reset, roughly thirty seconds in. Nothing but the host-silence heartbeat could have
done it.

### What this does not cover

A fault that takes out the chip before `spike_begin` arms anything, and a fault that
corrupts the scratch registers themselves. Both are recoverable only by holding BOOTSEL
while replugging, which is the one hands-on step this campaign cannot design away.
