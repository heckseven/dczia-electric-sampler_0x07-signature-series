## 1. Open bug — start here

**Streamed samples play exactly once. The second hit kills the track.**

Symptom: pads 3 and 4 go silent within seconds of playing. Those are the only
two tracks that stream (`hh_hats-open_1` 37 KB, `cymbals_crucible-edge_1`
66 KB); the kick and snare are under `MAX_RAM_SAMPLE` and keep playing.

Evidence — file position across repeated hits on one streamed `WaveFile`:

```
before any play      : tell=44
after play 0 (0.5s)  : tell=15916   playing=True
after play 1 (0.5s)  : tell=556     playing=False
after play 2 (0.5s)  : tell=556     playing=False   <- dead from here on
```

The second `voice.play()` does not rewind. It drops the position to 556 and
the voice never plays again. **Nothing raises**, so `audio_errors` stays 0 and
the badge cannot tell a hit was lost.

The damage reaches the file handle, which is why seeking cannot recover it:

```
tell: 556
seek ok, tell now 556      <- seek(0) silently did nothing
read FAILED: OSError(5,)
WaveFile FAILED: OSError(5,)
```

Isolation — it is streaming, not retriggering:

```
streamed, retrigger every 0.5s (sample 1.16s)  1/40 failed to start
streamed, retrigger every 1.5s (finishes first) 1/20 failed to start
RAM sample, retrigger every 0.5s (sample 0.65s) 0/40 failed
```

It reproduces fast because the demo pattern fires the hats every **500 ms**
against a **1160 ms** sample, so track 2 always reaches its second play
immediately.

### What was tried and reverted

1. Detect `not voice.playing` after `play()` and retry once. Measured in real
   use: `silent=3 lost=0` — the retry worked every time and was **irrelevant**,
   because the failing hits do report `playing=True` briefly and then produce
   silence.
2. Rebuild the `WaveFile` per hit (`seek(0)` + new `WaveFile`, same buffer):
   12/30 hits survived.
3. Also reopen the file per hit (needed, since the handle is spent): still
   12/30, and **13.8 ms per trigger** inside the audio path.

None of this was committed. Reverted; the tree is clean at `5793cb8`.

### Recommended next step

**Keep kit samples under `MAX_RAM_SAMPLE` so nothing streams.** RAM playback
never failed once (0/40) in the same test that broke streaming repeatedly.
24 KB at 16 kHz mono 16-bit is **0.77 seconds**. 69 of the 98 samples on the
card already fit.

Concretely: add `--max-seconds` (with a short fade, or a hard cut sounds bad on
a cymbal) to `Tools/convert_samples.py`, reconvert the two long ones, redeploy.

The deeper question — whether an `audiocore.WaveFile` can be replayed reliably
at all on CircuitPython 10.2.1 — may not be fixable from Python. Worth checking
CircuitPython issues before spending more on it.

### Also unexplained

Idle collection rate rose from 1-2 per 5 s to 3-7 per 5 s with the transport
stopped and nothing touched, trending upward. Suspect the 60-second idle
screensaver allocating per frame. Not investigated.

## 3. Resuming on another machine

**`pytest` is not installed system-wide** and pip refuses the system Python.

```
python3 -m venv ~/.venvs/dczia && ~/.venvs/dczia/bin/pip install pytest
~/.venvs/dczia/bin/python -m pytest        # 1125 passed, 1 skipped
```

**`mpy-cross` is not vendored** and must match the badge's CircuitPython
version exactly — the PyPI `mpy-cross` is MicroPython's and emits magic `0x4d`
where CircuitPython needs `0x43`.

```
https://adafruit-circuit-python.s3.amazonaws.com/bin/mpy-cross/linux-amd64/mpy-cross-linux-amd64-10.2.1.static
sha256 c85a9bdb3db06d8e77b600d1d025686b753448be89bb14082ee6e3a01e3c13fe   (1411184 bytes)
```

**Deploy:** `python3 Tools/build.py -o /media/<you>/CIRCUITPY --mpy-cross ./mpy-cross`

The badge currently runs the bytecode build of `5793cb8`. A deploy is not
finished until you have watched a boot: count USB re-enumerations and look for
a `Traceback` over ~100 s. Identical files prove the copy, not the badge — a
crash with no traceback is a hard fault or a watchdog reset, not an exception.

**Proving a regression test is real:**
`DCZIA_PRODUCTION_DIR=/path/to/old/Software/Production pytest`
A test that passes there is not testing what it claims. Two tests written this
session passed against the broken code until they were rewritten.

## 4. Hardware facts that cost time to learn

**The badge exposes the SD card over USB read-only.** `/dev/sdb` is CIRCUITPY,
`/dev/sdc` is the card (`ID_MODEL=Pico_W`, `scsi-0:0:0:1`), and
`/sys/block/sdc/ro` reads `1`. That is not a lock tab and no `remount,rw` will
move it: `setup.py` mounts the card for the firmware, and FAT can only be
writable from one side. **To write it, put the card in a reader.** Find it by
volume id, never by device node.

**The SD driver truncates card capacity to 16 bits.** A 64 GB card reads as
27.69 GiB:

```
C_SIZE the card really has : 122239   (0x1DD7F, needs 17 bits)
C_SIZE the badge computed  :  56703   (0x0DD7F)
low 16 bits of the real one:  56703   exact match
```

This breaks at `C_SIZE = 65536`, i.e. **32 GiB** — the SDHC/SDXC boundary. Any
card over 32 GB reports wrapped, and a filesystem spanning the whole card then
claims sectors the badge is certain do not exist, so the mount fails with EIO.
Workaround in place: the card is partitioned to end at sector **58,000,000**,
inside the badge's believed 58,064,896, and holds all 98 samples.

**Other measured numbers**

```
flash free, source vs bytecode        22 K  ->  252 K
free RAM at handover                27568  ->  25264   (bytecode is WORSE)
largest contiguous block             6912  ->  11840   (bytecode is better)
card throughput, 1 KB reads                  1168 KB/s
WaveFile buffer                    capped 8-1024 bytes, still, in 10.2.1
gc.collect()                                    25-27 ms
audio buffer (Mixer default 1024 B)               32 ms
main loop while streaming                  ~125 passes/s
MAX_RAM_SAMPLE 24 KB at 16 kHz mono            0.77 s
```

Two things I asserted and later disproved, so nobody re-derives them:

- **CircuitPython discards docstrings.** 5450 bytes of docstring compiled to
  the same bytecode as a one-line comment. Converting all 270 moved the output
  356 bytes. It is not a memory optimisation. (`mpy-cross -O3` does save ~5 KB,
  by stripping line numbers — which makes every traceback useless on a badge
  whose only debugging is USB serial.)
- **Bytecode does not free RAM.** It costs 2,304 bytes of total heap and buys a
  71% larger contiguous block. The contiguous half is the one that runs out.
